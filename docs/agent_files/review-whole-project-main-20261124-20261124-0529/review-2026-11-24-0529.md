## High severity

### H1 — Incomplete model coding responses silently become complete-looking counts

**Evidence:** [code_pass.py:246](../../../engines/miti/src/onolys_miti/code_pass.py#L246), [code_pass.py:265](../../../engines/miti/src/onolys_miti/code_pass.py#L265), [code_pass.py:335](../../../engines/miti/src/onolys_miti/code_pass.py#L335).

The code pass only iterates volleys that the model returned. It does not require one response for every requested volley, and the quality gate expressly accepts `total == 0`. Missing volleys, empty utterance arrays, or omitted clinician speech therefore contribute no dropped utterances and no warning. The final assembly skips any missing volley. A syntactically valid but incomplete response can yield silent undercounts, including every behavior count being zero, while the rest of the pipeline produces a report.

**Benign local confirmation:** a fake LLM was given two synthetic clinician volleys and returned `{"volleys": []}`. `code_pass` succeeded after one call with **zero instances and zero warnings**. No provider or user content was involved.

**Proposed fix:** validate the response volley ID multiset against the requested set, reject duplicate/missing/unknown entries, and require an explicit located utterance representation for clinician content, including uncoded speech. Use a bounded retry and then fail the coding run if completeness cannot be established. Test empty, omitted, duplicate, and partially covered volleys.

### H2 — Evaluation units are permanently stranded after a claimed request is interrupted

**Evidence:** [runs.py:557](../../../eval/backend/src/onolys_eval_backend/runs.py#L557), [runs.py:566](../../../eval/backend/src/onolys_eval_backend/runs.py#L566), [runs.py:713](../../../eval/backend/src/onolys_eval_backend/runs.py#L713), [runs.py:716](../../../eval/backend/src/onolys_eval_backend/runs.py#L716).

An evaluation unit transitions from `queued` to `running` without an expiring lease or claim token. Any later delivery sees `running`, returns immediately, and the HTTP task endpoint acknowledges success. A process termination, request cancellation, or failed final repository write after the claim can leave the unit and parent run permanently in progress. Cloud Tasks redelivery cannot repair it, and cancelling a run only terminalizes queued units.

**Benign local confirmation:** a synthetic engine raised `asyncio.CancelledError` after a claim. The unit remained `running`; a second `execute_unit` returned without work and left `completed_units == 0`. This simulated interruption locally without terminating a real service.

**Proposed fix:** persist a lease and attempt owner; return a retryable response while another unexpired owner is active; reclaim expired leases; fence final writes to the owning attempt; add a bounded stale-run reconciliation path. Test interruption and final-write failure after provider completion as well as concurrent claims.

### H3 — Session transitions validate an old state and then overwrite newer terminal state

**Evidence:** [machine.py:123](../../../api/src/onolys_api/jobs/machine.py#L123), [machine.py:170](../../../api/src/onolys_api/jobs/machine.py#L170), [firestore.py:273](../../../api/src/onolys_api/repo/firestore.py#L273).

`advance` reads session/status, checks the transition, and later calls `update_session`; the Firestore implementation uses an unconditional batch. A cancellation or deletion marker committed between the read and write is not rechecked. In-flight validation, transcription or report completion can restore an active/ready state over `cancelled` or `deleting`. The batch keeps the two documents mutually consistent but does not make the state decision atomic.

**Evidence status:** source-confirmed race; the reference lines were rechecked. Existing cancellation tests do not establish that the generic read/check/write operation has compare-and-set semantics across independent service instances.

**Proposed fix:** expose a transactional transition operation that reads the current state and writes the session/status together, checking allowed source states and terminal guards inside the transaction. Fence asynchronous results against a run/step version. Add deterministic two-instance interleaving tests around the transition commit.

### H4 — Report publication and terminal bookkeeping can disagree

**Evidence:** [run.py:109](../../../api/src/onolys_api/jobs/run.py#L109), [run.py:197](../../../api/src/onolys_api/jobs/run.py#L197), [run.py:209](../../../api/src/onolys_api/jobs/run.py#L209), [runs.py:151](../../../api/src/onolys_api/routes/runs.py#L151), [runs.py:281](../../../api/src/onolys_api/routes/runs.py#L281).

The worker persists a report, updates run metadata, and transitions the session to readiness in separate operations. There is also a cancellation window after the last active check and before report persistence. A failure or terminal-state race can leave a stored, retrievable report while the session/run is failed or cancelled. The existence of a final report then blocks the normal retry path, so users can be left with contradictory status and no supported recovery. A redelivery can repair some failures, but terminal worker failures and cancellation can prevent that repair.

**Evidence status:** source-confirmed publication race; the reference lines were rechecked, without injecting a cloud outage.

**Proposed fix:** publish the report reference, run completion metadata, session readiness and reservation outcome through one fenced transaction after storing any large blob. Read routes should expose only committed publications; a reconciler should repair pre-existing partial publication. Include cancellation and transient/final bookkeeping-failure cases.

### H5 — Failed-upload discard can delete a session after cancellation succeeded

**Evidence:** [firestore.py:400](../../../api/src/onolys_api/repo/firestore.py#L400), especially [firestore.py:414](../../../api/src/onolys_api/repo/firestore.py#L414).

The discard transaction checks that the session is not cancelled and writes an upload-failed status stub. It leaves the session document unchanged, commits, and then recursively deletes the session outside that transaction. Cancellation can commit successfully in the gap; the subsequent recursive deletion removes that cancelled session and its retained data. The cancellation guard protects only the earlier snapshot.

**Evidence status:** source-confirmed cleanup race; the reference lines were rechecked.

**Proposed fix:** atomically mark an exclusive discard/tombstone state before destructive cleanup, require cancellation and other transitions to honor it, and have cleanup verify an ownership/version marker. Preserve the invariant that a successfully cancelled session is not later discarded as a bad upload. Add a deterministic cancellation-between-commit-and-cleanup test against the emulator.

### H6 — The production Firestore adapter drops failure-policy and progress fields

**Evidence status: source-confirmed.** [web/src/api/firestoreListener.ts:46](../../../web/src/api/firestoreListener.ts#L46) (mapping ends at line 59) emits only the older status fields. It discards `error_kind`, `retries_left`, `counted`, `started_at`, `stage_started_at`, `waited_ms`, `audio_s`, `progress_next`, and `stage_expected_s` even when the server document contains them. These fields are part of `SessionStatusDoc` ([web/src/api/statusListener.ts:28](../../../web/src/api/statusListener.ts#L28)) and REST fallback preserves them ([web/src/features/session/useSessionStatus.ts:32](../../../web/src/features/session/useSessionStatus.ts#L32)).

Impact: normal production live listeners treat every failed session as a permanent internal error, because `failureView` switches on the now-missing `error_kind` ([web/src/api/errors.ts:100](../../../web/src/api/errors.ts#L100)), hiding Retry for retryable failures and the correct file-replacement action for user-file failures, and potentially claiming that a charged failure did not count. Elapsed remains zero without `started_at`; upload overall progress cannot follow actual bytes without `progress_next`; timed interpolation uses fallback timing and the wrong stage ceiling ([web/src/features/session/progress.ts:54](../../../web/src/features/session/progress.ts#L54), `:72`). Mock mode's emitter bypasses this adapter, so mock browser tests pass while live behavior is broken. Existing `firestoreListener.test.ts` also asserts only the obsolete subset.

Suggested fix: map all current `SessionStatusDoc` fields with timestamp conversion/defaults, and test adapter-to-session behavior using realistic failed, uploading and timed-state snapshots, not only mapper shape.


## Medium severity

### M1 — The validated audio and published original can be different object generations

**Evidence:** [validate.py:230](../../../api/src/onolys_api/jobs/validate.py#L230), [validate.py:263](../../../api/src/onolys_api/jobs/validate.py#L263), [validate.py:266](../../../api/src/onolys_api/jobs/validate.py#L266), [gcs.py:56](../../../api/src/onolys_api/storage/gcs.py#L56).

The worker validates, converts and hashes downloaded staging bytes, but publishes the original by copying the current remote object later. That copy/delete carries no generation precondition. A legitimate overlapping/retried signed PUT can replace the staging object in the gap, so the stored original may differ from both the validated canonical recording and its metadata/hash.

**Evidence status:** source-reviewed object-generation data flow.

**Proposed fix:** publish the already validated local bytes, or bind download, copy and delete to the same immutable GCS generation using preconditions. Check the stored recording hash against the published original in a local generation-aware fake test.

### M2 — Password-reset acceptance is followed by nondurable work after the response

**Evidence:** [auth_email.py:92](../../../api/src/onolys_api/routes/auth_email.py#L92), [auth_email.py:123](../../../api/src/onolys_api/routes/auth_email.py#L123), [services.tf:36](../../../infra/modules/environment/services.tf#L36), [services.tf:54](../../../infra/modules/environment/services.tf#L54).

The API returns 202 and runs the password-reset send as an in-process background task. The API service uses request-based CPU allocation (`cpu_idle = true`), and a process/revision termination after the response can lose this task. Failed delivery is logged but cannot be retried by the requester based on the deliberately generic response. This creates apparently successful resets that never arrive.

**Evidence status:** configuration and implementation inspection; no live mail or service lifecycle experiment.

**Proposed fix:** durably enqueue the send before acknowledging it, with bounded retry and deduplication. Preserve the generic response for account privacy and keep sensitive email/link material out of logs.

### M3 — Evaluation transcription can poll forever without a time budget

**Evidence:** [uploads.py:292](../../../eval/backend/src/onolys_eval_backend/uploads.py#L292), [uploads.py:312](../../../eval/backend/src/onolys_eval_backend/uploads.py#L312), [uploads.py:338](../../../eval/backend/src/onolys_eval_backend/uploads.py#L338).

Whenever STT returns pending, the handler enqueues a new task after 15 seconds. It never checks upload age, a persisted deadline or a total poll count. New tasks each have a fresh delivery retry budget, so queue `max_attempts` does not bound the chain. A provider operation that stays pending indefinitely leaves the upload stuck and schedules work indefinitely.

**Evidence status:** source only. The existing tests exercise pending and completion but do not establish a maximum chain age.

**Proposed fix:** persist a transcription deadline/budget, fail pending operations after it, and add a stale-upload reconciliation path for a lost last poll. Test a fake provider that remains pending beyond the deadline.

### M4 — Direct transcript uploads block the event loop on synchronous storage

**Evidence:** [transcript.py:70](../../../api/src/onolys_api/routes/transcript.py#L70), [transcript.py:122](../../../api/src/onolys_api/routes/transcript.py#L122), [transcript.py:138](../../../api/src/onolys_api/routes/transcript.py#L138).

The route is async to stream the body, but calls synchronous repository/blob methods and first-run scheduling directly before and after the awaits. Production Firestore/GCS latency therefore blocks the ASGI event loop for other requests on the instance; combined mode also shares that loop with voice handling. Small uploads can still incur several remote operations.

**Evidence status:** source inspection, not a load test.

**Proposed fix:** keep bounded asynchronous body reading, then run the synchronous persistence/transition sequence in a thread or use asynchronous clients. Preserve transactional state guards while doing so. Verify concurrent health/status requests remain responsive with a deliberately slow local repository fake.

### M5 — Admin token verification performs blocking certificate I/O inside ASGI middleware

**Evidence:** [middleware.py:20](../../../admin/auth/src/onolys_admin_auth/middleware.py#L20), [verifier.py:29](../../../admin/auth/src/onolys_admin_auth/verifier.py#L29), [verifier.py:53](../../../admin/auth/src/onolys_admin_auth/verifier.py#L53).

The async middleware invokes the synchronous verifier directly. Certificate refresh can perform a five-second HTTP request while holding the cache lock; concurrent authenticated requests share that path. A cold/expired cache or certificate endpoint failure can block the event loop and serialize unrelated requests. Evaluation uses the same admin-auth boundary.

**Evidence status:** source-reviewed synchronous call path.

**Proposed fix:** offload token verification from the event loop, keep single-flight certificate refresh, and add failure cooldown/backoff so a failed refresh does not immediately trigger serialized repeated fetches. Verify responsiveness and refresh coalescing with a slow local fake transport.

### M6 — Opening another account's verification link while signed in falsely says it is verified

**Source-only finding; high confidence.** [web/src/auth/pages/AuthAction.tsx:108](../../../web/src/auth/pages/AuthAction.tsx#L108) returns “Already verified” whenever the current signed-in account has `emailVerified`, without checking which account owns `oobCode`. Suggested fix: inspect the action code's account before deciding it is already verified, or always offer the explicit Verify action for a supplied code; do not infer the link's state from an unrelated current user. Add a two-account action-link test.

### M7 — Leaving while microphone startup is pending can create an orphan recording/socket

**Source-only finding; high confidence; overlaps root's observation.** [web/src/features/interview/InterviewPage.tsx:136](../../../web/src/features/interview/InterviewPage.tsx#L136) allocates the engine locally and awaits `engine.start()` at line 138, but stores it in `engineRef` only at line 146. ### M9 — A rejected token refresh is unhandled during practice relay authentication

**Source-only finding; high confidence.** [web/src/features/interview/live/controller.ts:107](../../../web/src/features/interview/live/controller.ts#L107) starts `opts.getToken().then(...)` without a rejection handler. The real service returns Firebase `getIdToken()` promises ([web/src/auth/firebaseService.ts:208](../../../web/src/auth/firebaseService.ts#L208)); network/token-refresh errors can reject. The controller neither closes the socket nor enters an error/reconnect state in that branch, leaving an unhandled rejection and Connecting until the peer closes (if it does), with the microphone/recorder already started.

Suggested fix: handle rejection through the controller's terminal/retry policy, close the unauthenticated socket, and expose an actionable error; add an existing-controller-style rejected-token test.


### M10 — An open session page does not trigger stale settlement for upload, validation or coding

**Evidence status: source-confirmed cross-layer gap.** [useSessionStatus.ts:119](../../../web/src/features/session/useSessionStatus.ts#L119) only performs the periodic GET nudge for transcription, while [stale.py:31](../../../api/src/onolys_api/jobs/stale.py#L31) and [stale.py:64](../../../api/src/onolys_api/jobs/stale.py#L64) settle upload, validation and running states lazily during reads. A listener can remain connected with the last active snapshot after its worker chain has stopped, and the open page never invokes the server path that marks it stale.

**Proposed fix:** schedule a bounded status read for every active state that depends on lazy settlement, or move stale reconciliation to a durable server sweep. Test a connected listener that receives no further snapshots after work stops.

### M11 — Upload jobs retain completed recordings, and uploads have no configured XHR deadline

**Evidence status: source-confirmed.** [uploader.ts:41](../../../web/src/features/upload/uploader.ts#L41), [uploader.ts:106](../../../web/src/features/upload/uploader.ts#L106), [uploader.ts:136](../../../web/src/features/upload/uploader.ts#L136) keep job/File references in the module registry until account change. **Proposed fix:** release the File after a completed transfer, remove settled jobs after consumers stop observing them, evict on session deletion, and configure a suitable transfer deadline with resumable/retry behavior. Verify memory ownership across multiple completed/deleted recordings and a stalled local upload.

### M12 — A lost session-link response can strand a finished practice recording

### M13 — Transcript-only processing never initializes its elapsed clock

### Keeping PR feedback within five minutes

**Five minutes means the required PR gate finishes within 300 seconds from the first CI job starting, including checkout, dependency setup, builds, emulator/browser startup, artifact transfer and aggregation.** Target 270 seconds, leaving 30 seconds of headroom. Queue delay is recorded separately because runner availability is outside workflow execution; this plan does not claim a five-minute event-to-result guarantee while jobs wait for runners. A five-minute timeout on each parallel job is insufficient: the existing routing stage and coverage tail are serial dependencies.

Current implementation:

- [ci.yml:16–82](../../../.github/workflows/ci.yml#L16) runs the entire guard suite before emitting change flags, delaying every package job. Separate quick classification from parallel guard validation; the final required gate must still require those guards.
- [ci.yml:213](../../../.github/workflows/ci.yml#L213) and [ci.yml:249](../../../.github/workflows/ci.yml#L249) run API unit/emulator jobs in parallel, followed by [ci.yml:300–330](../../../.github/workflows/ci.yml#L300)'s fresh environment setup, artifact merge and 94% coverage gate. Count that tail explicitly; avoid resynchronizing the entire API environment solely to combine coverage if a pinned coverage-only reducer can produce the identical result.
- [ci.yml:514](../../../.github/workflows/ci.yml#L514) serializes web checks, covered unit tests, flaky tests and build, while [ci.yml:557](../../../.github/workflows/ci.yml#L557) starts the whole browser matrix. [ci.yml:166](../../../.github/workflows/ci.yml#L166), [ci.yml:432](../../../.github/workflows/ci.yml#L432) and [ci.yml:478](../../../.github/workflows/ci.yml#L478) include image builds. Current job timeouts are ten minutes, not evidence that the five-minute target holds.

| Critical-path stage | Proposed execution envelope | Included work / admission rule |
|---|---:|---|
| Quick routing | 20 s | Checkout/base comparison, existing dependency propagation, outputs. Full guard verification starts in parallel and remains required. |
| Parallel required workers | 220 s maximum | Each worker includes its own checkout/cache restore/install and execution.
