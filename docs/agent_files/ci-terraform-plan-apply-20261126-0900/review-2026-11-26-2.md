# Review 2026-11-26 round 2: ci/terraform-plan-apply

Verdict: NEEDS_CHANGES. All items below were fixed in the follow-up round, together with the owner's redesign (last section).

## Round 1
All round-1 findings (S1-S5, B1-B3, A1-A3, should-fix list in `review-2026-11-26-1.md`) verified fixed.

## Must-fix
- **Bug: apply/deploy gating on implicit `success()`.** When one upstream leg failed or was skipped, the default `success()` skipped every dependent job, including unrelated environments and jobs further down. Fix: every job after the infra jobs uses `if: ${{ !cancelled() && ... }}` with an explicit `needs.<job>.result` check per need (`success`, or `success`/`skipped` for infra jobs). `scripts/ci/test_terraform_pipeline.py` parses those expressions and evaluates them against simulated job results (infra disabled, no changes, changes, failed plan, failed apply, failed admission) instead of substring matching.
- **Bug: staging example tfvars did not match live.** `examples/environment-staging.tfvars.example` had `resend_secret_wired = false`; the operator's last-used staging inputs and live staging (api and worker reference secret `resend-api-key-staging`, checked read-only with `gcloud run services describe`; `firebaseauth.admin` and `workerAuthEmail_staging` grants present) have it wired. CI would have unwired email. Fix: example set to `true`. Eval's example matches the operator inputs except the deploy-managed `git_sha` (live eval has no Resend wiring). `infra-pipeline.md` now requires, before enabling staging/eval, a read-only plan with the example tfvars that shows changes only in `module.terraform_ci`, as already required for prod.

## Notes
- **Plan metadata retention.** `tf-meta` / summary artifacts expired after 3 days, shorter than a possible approval wait. Fix: plan hashes now travel as job outputs (no `tf-meta` artifacts); the PR summary artifacts are kept 7 days, matching the `plans/` bucket lifecycle.
- **Doc claim about the environment.** `infra-pipeline.md` said the prod apply could not get a token without the environment; GitHub creates an unknown environment automatically and unprotected. Moot now that apply uses the existing, protected `production` environment; the doc states that the approval is the environment's protection rule (an owner setting) and that the WIF condition only proves the job ran in `production`.
- **`plan_extra_*` validation.** The `plan_extra_permissions` regex accepted data reads (`datastore.entities.*`, `storage.objects.*`, `firebaseauth.users.get`, `cloudtasks.tasks.*`, `logging.logEntries.*`), and `plan_extra_roles` had no validation. Fix: shared deny list `infra/modules/terraform-ci/plan-deny.json`, used by both variable validations (roles limited to `*.viewer`/`*Viewer` and not denied) and by `test_terraform_ci_permissions.py`; mocked `terraform test` runs prove the rejections.

## Owner decision after review
Fold infra into the deploy pipelines: one pipeline per environment (infra plan at the deployed commit, apply only if it has changes, then the app), `terraform.yml` plans PRs only, prod infra and app released by one shared `production` approval, and prod rollback/promote also plans and applies infra at the target commit. Implemented in the same follow-up round; see `docs/reference/infra-pipeline.md` and ADR 0026.
