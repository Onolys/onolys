# PRD: SP05 Eval backend on the prod pipeline

Repo/branch: Onolys/iaudit / `session-report-ux` · Depends on: SP04 (`is_eval` run path), SP03 (env, deploy config) · Owns: `eval/backend/src/onolys_eval_backend/{app,config,services,runs,read_runs,repository,storage,queue,catalog,uploads}.py` + new `eval_sessions.py`, `eval_scheduler.py`, `eval_delete.py`, `eval_view.py`; `eval/backend/{pyproject.toml,Dockerfile,tests}`; `eval/web/src/{api.ts,Runs.tsx,Root.tsx}` (history delete only); additive `api/src/onolys_api/repo/{models,base,firestore,fake}.py` (SessionDoc `eval` block, `get_runs`, `delete_run_data`) and a `routes/transcript.py` helper extraction · SP06 reads this SP's listing; SP07 owns compare screens.

## TL;DR
Eval stops being a second pipeline. A dataset session or upload is imported once as a prod `SessionDoc` + `TranscriptDoc` (id derived from a content fingerprint, so re-import is a no-op). Each combo x repeat is one prod `RunDoc` (via SP04's `create_run(is_eval=True)`) run by the one prod worker. A `tick` task per eval run creates the next run per session when the previous one finishes (never two active on a session), allows at most 2 sessions in flight per AI provider across the deployment, retries transiently failed runs as new RunDocs, and rolls status up on an `eval_runs` doc. The whole thing is server-driven: the owner can close the browser and the eval runs to completion. Cancel stops further runs, keeps everything already completed and ends the eval run as `partial`. Deleting an eval run deletes exactly its RunDocs, ReportDocs, report blobs and run output files; sessions, transcripts, datasets and gold stay. The eval web keeps working through a view adapter; only a Delete action is added.

## Goals / Non-Goals
**Goals:** one session per (dataset, session, inputs) shared by all eval runs; one RunDoc per cell (`n_runs=1`); decision-9 scheduling with a per-provider concurrency cap; eval runs complete with the browser closed; cancel that keeps completed work; decision-8 deletion; remove duplication items 1-7; existing eval features keep working; offline tests.
**Non-goals:** compare maths (SP06), compare screens (SP07), `is_eval` itself (SP04), Terraform (SP03), prod behaviour change, migration (data already deleted), per-user data separation, session garbage collection, replacing eval's own audio-upload STT flow.

**R5 Create.** `POST /v1/runs` (same request/response) validates selection (`validate_selection`, `plan_units`, unchanged), resolves `resolved_combos`, ensures sessions (R3), writes the group doc, enqueues `tick`. **R6 Scheduler (`eval_scheduler.py`, `POST /internal/tasks/tick`).** Cloud Task `{eval_run_id}-tick-{n}`; handler is a no-op unless `n == tick_seq`. Each tick, in this order: (1) enqueue tick `n+1` (delay ~10 s) BEFORE any work, as prod's transcribe poll does, so a crash cannot end the chain [verified: `jobs/transcribe.py` docstring]; (2) for every session with `active_run_id`, `repo.get_runs` and fold terminal RunDocs into the doc (`status`, usage, cost via `PriceBook` on `run_info.usage`); (3) failed RunDoc whose `kind_for_code(error)` is transient and attempts left (2 retries) -> new run for the same cell after backoff (5 s / 20 s); every other failure, including a run failed by a `code_version` change (deploy), stays `failed` and is shown as failed: no retry, no re-create; (4) if `cancel_requested`, skip filling (R7); else fill free slots: sessions without an active run, in `order`, take the next cell if the provider has a free slot (below), recompute `resolved_route` and compare with `saved_config.resolved_combos[combo_key]` (mismatch -> cell `failed: execution_config_changed`, today's drift rule), then `create_run(is_eval=True, eval_spec, run_id=<deterministic>)`; (5) all cells terminal -> roll up status and stop re-enqueueing. **Per-provider cap.** A cell's provider is the first segment of its `resolved_route.litellm_id` (`<provider>/<tier>`; today Anthropic and Gemini) [verified: `catalog.py:138`, `runs.py:606`]. Rule: at most `EVAL_MAX_PER_PROVIDER` (2) sessions have an active run on one provider across ALL eval runs in the deployment, in addition to one active run per session. To be race-free across concurrent ticks of different eval runs, a slot is claimed in a Firestore transaction on a small `eval_slots/{provider}` doc (`holders: {run_id: eval_run_id}`, claim only when `len(holders) < cap`) BEFORE `create_run`, and released when the run is folded terminal, on cancel, or on delete; each tick also drops holders whose RunDoc is terminal or whose eval run is gone (crash recovery). Slots go to whichever tick claims first; a session whose slot is taken waits (its cell is not skipped) and is retried next tick. The cap is a config value, not code; a new provider needs no change. Deterministic `run_id = sha256(eval_run_id|sid|combo_key|repeat|attempt)[:32]`, so a crash between creation and recording is recovered (`ConflictError` = already created). `create_run` returning `not_ready` (session busy, e.g. another eval run is using the same session) = skip this tick, retry next; SP04's allowed states make the repo itself refuse a second active run on a session (defence in depth for decision 9) [verified: `firestore.py:1202`]. `GET /v1/runs/{id}` re-enqueues a tick (`-r<epoch>` name) when `last_tick_at` is stale while active, as uploads do for transcribe [verified: `uploads.py:468-479`]. **Leave the page.** Nothing in the browser drives a run: creation enqueues the tick, the tick chain and the prod worker do all work, and `GET` is only a stale-tick safety net. The owner can close the tab or the browser and the eval runs to completion; reopening History or the run detail shows the live current status and counters from the group doc.
**R7 Cancel.** `POST /v1/runs/{id}/cancel` already exists (sets `cancel_requested`, finalizes queued units) [verified: `runs.py:493 cancel_run`; `repository.py:131,270`; run-detail button `Runs.tsx:180`] and is reworked for the group doc. Semantics: no new runs start; cells not yet started become `cancelled` (reason `cancelled`); runs in progress are stopped best effort (below): if the stop lands the cell is `cancelled`, if the run finished first the result is kept (`done`); everything already completed is kept, readable and comparable. Final status when all cells are terminal: `partial` if at least one non-human run completed (`done`), else `cancelled` (matches today's rollup [verified: `runs.py:476-486`]). `cancelled_at` is stored at the request time and returned so the UI can say "cancelled at <time>, X of Y runs done"; `partial` without `cancelled_at` still means some runs failed (as today). Idempotent: a second cancel changes nothing and returns the current status; cancelling a terminal run (`done|partial|failed|cancelled|deleting`) is a 200 no-op, an unknown id is 404. Allowed for any allowlisted user, same as delete (R8). Released provider slots (R6) free at once. **In-flight stop (best effort).** Prod session cancel is never used (terminal, would block shared sessions) [verified: `jobs/machine.py:59`]; `RunStatus` has no `cancelled` [verified: `models.py:33`]. Instead the tick sets an additive internal flag on the run (`RunDoc.eval.cancel_requested`, via one new `repo` method) and the worker's stage-boundary check, which today only looks at session state [verified: `jobs/run.py:198`, `jobs/alive.py`], fails an `is_eval` run with code `eval_cancelled` when it sees the flag; the tick folds that into cell `cancelled`. Prod runs are untouched (flag exists only on eval runs). If this worker edit is not accepted, the fallback is that in-flight runs finish and are kept (still correct, just later; see Open Questions).
**R8 Delete.** `POST /v1/runs/{id}/delete {confirm_run_id}` (POST keeps CORS methods unchanged [verified: `app.py` `allow_methods`]); `confirm_run_id` must equal the path id. Allowlisted user only (existing middleware). Refused 409 `run_active` unless status is terminal (`done|partial|failed|cancelled`): cancel first, wait for the in-flight runs to stop, then delete. Accepted: set `status=deleting` (hidden from tick, shown in History as `deleting`), return 202, enqueue `delete` task `{id}-delete-{n}`. Handler is idempotent and resumable; for every ref in the group doc (all attempts): (1) delete outputs under `{uid}/{sid}/runs/{run_id}/`, (2) delete ReportDoc and its blob pointer, (3) delete RunDoc (`repo.delete_run_data`), and last (4) delete the group doc, so a retry always still has the refs. Failure at any step leaves `deleting` + `delete_error` code, task retries with a new name; the same POST again is a safe retry. Never deleted: sessions, TranscriptDocs, transcript blobs, datasets, `gold/*`, other eval runs' RunDocs (refs list only this run's ids; shared-session test below). No session field is repaired: report versions are `max+1` over existing reports so gaps are harmless [verified: `firestore.py:333-336,376`], eval reads reports by run id, and all runs of the deleted group are terminal so no session is left `running`. History shows `deleting` until the group doc is gone, then the row disappears; detail returns 404.

## Architecture
```
eval web --(allowlist)--> eval-backend: POST /v1/runs
   ensure_session x N --> SessionDoc+TranscriptDoc (sid=fingerprint), gold/<sha>.json
   eval_runs/{id} (grouping) ; enqueue tick
tick (self re-enqueue ~10s) --> claim eval_slots/{provider} --> create_run(is_eval=True, run_id=det) --> start_run txn --> Cloud Task run
                                  one active run per session, <= 2 sessions in flight per provider (deployment-wide)
prod worker (same image/handler) --> RunDoc + ReportDoc + {uid}/{sid}/runs/{run_id}/*
eval-backend read --> group doc (progress) ; RunDocs/ReportDocs/gold (detail, compare)
```
Endpoint shapes:
| Endpoint | Shape change |
|---|---|
| `POST /v1/runs`, `/rerun` | none (body and reply same); rerun now reuses pinned sids |
| `POST /v1/runs/{id}/cancel` | same route; now idempotent (no-op when terminal), reply adds `cancelled_at`; sets final status `partial`/`cancelled` |
| `GET /v1/runs` | same fields from group doc; `status` may be `deleting`; adds `cancelled_at` |
| `GET /v1/runs/{id}` | `units[]`: `unit_id` = run id (human: `human-<sid>`), `session_id` still the dataset session id, new `run_id`, `prod_session_id`, `attempt`; `output` never inline (web already fetches when absent [verified: `Runs.tsx` `UnitOutput`]); `compare` same shape via legacy builder until SP06 |
| `GET /v1/runs/{id}/units/{unit}/output` | same; source is ReportDoc (or gold) |
| `/v1/options`, `/v1/datasets*`, `/v1/uploads*`, `/v1/me`, `/healthz` | none (uploads move from `uploads/` to `eval-uploads/` prefix) |
| `POST /v1/runs/{id}/delete` | new |
| `/internal/tasks/unit` | removed; `tick`, `delete` added; `transcribe` kept |

Worked example: 12 sessions x 6 combos x 3 repeats = 216 RunDocs; with Anthropic and Gemini combos, at most 2 runs are active per provider (so <= 4 at once), each session runs its 18 runs in order, and a waiting session starts as a slot frees. The owner may close the browser; the run completes and History shows the result on return. Throughput is deliberately low; it is the owner's chosen spend/rate guard.

## Decisions
| # | Decision | Choice | Alternatives | Why |
|---|---|---|---|---|
| 1 | Session identity | `sid = fingerprint[:32]`, create-or-reuse | Firestore query by `(dataset_id, session_id)` | No index, race-free via exclusive create, pins transcript+goal+span so changed data never reuses a stale session |
| 2 | Owner uid | One shared eval uid | Uid per allowlisted email | Sessions are shared across users and runs; history is already global |
| 3 | Scheduler | Self-re-enqueued `tick` Cloud Task in eval-backend | Hook in prod worker; Cloud Scheduler sweep | No prod worker change; same pattern as eval's transcribe poll; no new infra |
| 4 | Refs location | Embedded in group doc | `units` subcollection | Item 4 removal; size bounded |
| 5 | Retry | New RunDoc per attempt, <=2 retries (5 s / 20 s), transient errors only; `code_version` failures stay failed | Eval-side in-unit loop; re-create on deploy drift | Prod worker already retries delivery; owner: do not worry about code version |
| 6 | Cancel | Stop creating, stop in-flight best effort via per-run eval flag, keep completed, final `partial`/`cancelled`, idempotent | Prod session cancel; let in-flight always finish | Prod cancel is terminal on the shared session; owner wants completed work kept |
| 7 | Delete | Refuse while active, ordered idempotent steps, group doc last | Auto-cancel then delete; delete session too | Late worker writes would orphan blobs; sessions are shared |
| 8 | Gold | Copy to `gold/<sha256>.json` at import | Read datasets bucket at compare time | Decision 7; immune to dataset edits; one read path |
| 9 | Compare bridge | View adapter feeds legacy `build_compare` | Drop compare until SP06 | Existing screens keep working |
| 10 | Image | Separate eval-backend image that imports `onolys_api` | Add an eval `SERVICE_MODE` to the api image | Keeps public app free of eval routes; resolves SP03's open point |
| 11 | Concurrency | Config cap 2 per provider, deployment-wide, via transactional `eval_slots/{provider}` | Global in-flight cap of 20 | Owner: at most 2 interviews in parallel per AI provider; race-free across eval runs |
| 12 | Server-driven | All progress on tick + worker; GET only a safety net | Browser polling drives runs | Owner can leave the page |

## Acceptance Criteria
- Import: same inputs -> same `sid`, one SessionDoc/TranscriptDoc, gold copied once; changed goal/span/transcript -> new `sid`; no `eval` field leaks into public session views or OpenAPI.
- Scheduler (fake queue/LLM): 3 sessions x 2 combos x 2 repeats never has two active RunDocs on a session; with combos on two providers and 2 eval runs at once, never more than 2 sessions with an active run per provider (cap from config, default 2; changing it changes behaviour); all 12 cells reach terminal; a crash between create and record yields no duplicate and no leaked slot; failed-transient runs get a new attempt (2 retries, 5 s / 20 s), a `code_version`-failed run and other failures stay failed with no new run.
- Leave the page: with no GET issued after create, a fake-queue run reaches terminal; a later `GET /v1/runs` and `/v1/runs/{id}` show the live then final status and counters.
- Cancel: no new run starts after the request; unstarted cells become `cancelled`; a run finished before the stop is kept `done`; a stopped in-flight run is `cancelled`; status ends `partial` with `cancelled_at` when >=1 run completed, `cancelled` when none; completed runs/reports stay readable; a second cancel and a cancel on a terminal run are 200 no-ops; slots are released; delete is still refused until terminal.
