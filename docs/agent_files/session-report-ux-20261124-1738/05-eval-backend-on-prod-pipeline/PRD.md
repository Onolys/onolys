# PRD: SP05 Eval backend on the prod pipeline

Repo/branch: Onolys/iaudit / `session-report-ux` · Depends on: SP04 (`is_eval` run path), SP03 (env, deploy config) · Owns: `eval/backend/src/onolys_eval_backend/{app,config,services,runs,read_runs,repository,storage,queue,catalog,uploads}.py` + new `eval_sessions.py`, `eval_scheduler.py`, `eval_delete.py`, `eval_view.py`; `eval/backend/{pyproject.toml,Dockerfile,tests}`; `eval/web/src/{api.ts,Runs.tsx,Root.tsx}` (history delete only); additive `api/src/onolys_api/repo/{models,base,firestore,fake}.py` (SessionDoc `eval` block, `get_runs`, `delete_run_data`) and a `routes/transcript.py` helper extraction · SP06 reads this SP's listing; SP07 owns compare screens.

## TL;DR
Eval stops being a second pipeline. A dataset session or upload is imported once as a prod `SessionDoc` + `TranscriptDoc` (id derived from a content fingerprint, so re-import is a no-op). Each combo x repeat is one prod `RunDoc` (via SP04's `create_run(is_eval=True)`) run by the one prod worker. A `tick` task per eval run creates the next run per session when the previous one finishes (never two active on a session), allows at most 2 sessions in flight per AI provider across the deployment, backs off and retries provider-overload failures (a per-provider cooldown pauses new slots for that provider only), retries an `internal_error` run once as a new RunDoc, skips a provider for the rest of the eval run after 5 failed runs in a row (its remaining cells become `skipped`), keeps every run's failure isolated from all other runs, and rolls status up on an `eval_runs` doc. The whole thing is server-driven: the owner can close the browser and the eval runs to completion. Cancel stops new runs from starting; runs already in progress finish and are kept (no change to the prod worker); the eval run ends as `partial`. Deleting an eval run deletes exactly its RunDocs, ReportDocs, report blobs and run output files; sessions, transcripts, datasets and gold stay. The eval web keeps working through a view adapter; only a Delete action is added.

**R6 Scheduler (`eval_scheduler.py`, `POST /internal/tasks/tick`).** Cloud Task `{eval_run_id}-tick-{n}`; handler is a no-op unless `n == tick_seq`. Each tick, in this order: (1) enqueue tick `n+1` (delay ~10 s) BEFORE any work, as prod's transcribe poll does, so a crash cannot end the chain [verified: `jobs/transcribe.py` docstring]; (2) for every session with `active_run_id`, `repo.get_runs` and fold terminal RunDocs into the doc (`status`, usage, cost via `PriceBook` on `run_info.usage`); (3) classify each failed RunDoc by `RunDoc.error`, the public error code string [verified: `models.py:344`; codes `error_map.py:43-54`]: `internal_error` -> ONE retry (`EVAL_INTERNAL_RETRIES`, a new RunDoc attempt, no delay); `upstream_unavailable` or `rate_limited` (provider overload/capacity, R6b) -> cooldown + re-try within the overload budget; every other code, including a run failed by a `code_version` change (deploy) and `deadline_exceeded`, stays `failed` and is shown as failed: no retry, no re-create. Every cell is handled inside its own try/except (R6c isolation), then the circuit breaker (R6d) is updated from each cell's FINAL outcome; (4) if `cancel_requested`, skip filling (R7); else fill free slots: sessions without an active run, in `order`, take the next cell if its provider is not skipped (R6d) and not cooling down (R6b) and has a free slot (below), recompute `resolved_route` and compare with `saved_config.resolved_combos[combo_key]` (mismatch -> cell `failed: execution_config_changed`, today's drift rule), then `create_run(is_eval=True, eval_spec, run_id=<deterministic>)`; (5) all cells terminal -> roll up status and stop re-enqueueing. **Per-provider cap.** A cell's provider is the first segment of its `resolved_route.litellm_id` (`<provider>/<tier>`; today Anthropic and Gemini) [verified: `catalog.py:138`, `runs.py:606`]. Rule: at most `EVAL_MAX_PER_PROVIDER` (2) sessions have an active run on one provider across ALL eval runs in the deployment, in addition to one active run per session. To be race-free across concurrent ticks of different eval runs, a slot is claimed in a Firestore transaction on a small `eval_slots/{provider}` doc (`holders: {run_id: eval_run_id}`, claim only when `len(holders) < cap`) BEFORE `create_run`, and released when the run is folded terminal or on delete (Cancel releases nothing early: in-flight runs finish, R7); each tick also drops holders whose RunDoc is terminal or whose eval run is gone (crash recovery). Slots go to whichever tick claims first; a session whose slot is taken waits (its cell is not skipped) and is retried next tick. The cap is a config value, not code; a new provider needs no change. Deterministic `run_id = sha256(eval_run_id|sid|combo_key|repeat|attempt)[:32]`, so a crash between creation and recording is recovered (`ConflictError` = already created). `create_run` returning `not_ready` (session busy, e.g. another eval run is using the same session) = skip this tick, retry next; SP04's allowed states make the repo itself refuse a second active run on a session (defence in depth for decision 9) [verified: `firestore.py:1202`]. `GET /v1/runs/{id}` re-enqueues a tick (`-r<epoch>` name) when `last_tick_at` is stale while active, as uploads do for transcribe [verified: `uploads.py:468-479`]. **Leave the page.** Nothing in the browser drives a run: creation enqueues the tick, the tick chain and the prod worker do all work, and `GET` is only a stale-tick safety net. The owner can close the tab or the browser and the eval runs to completion; reopening History or the run detail shows the live current status and counters from the group doc.
**R6a What already exists (build on it, do not duplicate).** The shared engine LLM client already (1) treats 429/529 (and `RateLimitError`) as `LLMRateLimited`, reads a numeric `Retry-After`, and re-sends within the request deadline with `backoff_s * 2^n * jitter(0.5-1.0)` waiting outside the per-route semaphore [verified: `engines/core/.../llm/litellm_client.py:148-170,354-370`; default `backoff_s=2`, `max_retries=3`, route `timeout_s=180`: `routes.py:68-69`, `routes.default.yaml:16`]; (2) retries timeouts/bad output/unavailable (including 503 and other 5xx, which are NOT on the rate-limit path) up to `route.max_retries` with doubling delay [verified: `litellm_client.py:306-318`]; (3) marks 408/429/500/502/503/504/529, timeouts and connection errors transient [verified: `errors.py:39-62`]. The worker then maps any transient LLM failure to the public code `upstream_unavailable` and any permanent LLM failure (400, bad output) to `internal_error` [verified: `error_map.py:_classify_llm`, `KIND_BY_CODE`; `rate_limited` is a public code but `classify` never emits it for LLM errors]; transient failures get one task-level retry (`MAX_ATTEMPTS = 2`) before the run records `failed` [verified: `jobs/queue.py:37`, `jobs/run.py:99-117`]. All of that is bounded by the run's task deadline, so it ends and a run still can fail with `upstream_unavailable` when a provider stays overloaded. The `RunDoc` keeps only the public code, not the HTTP status or `Retry-After` [verified: `models.py:344`]. SP05 therefore adds only the scheduler-level layer below: it never re-implements in-call backoff, never changes the prod LLM client or worker, and treats `upstream_unavailable`/`rate_limited` as the provider-capacity class.
**R6b Overload backoff and provider cooldown.** A cell whose run failed with `upstream_unavailable` or `rate_limited` (after the existing in-call and task-level handling above) is not an ordinary failure: the cell becomes `waiting` and is retried as a new RunDoc attempt after a wait of `min(120, 15 * 2^k) s * jitter(0.5-1.0)` (k = overload re-tries so far; a `Retry-After` hint is already honoured inside the call; the RunDoc does not expose it, see Open Questions). Total overload wait per cell is bounded by `EVAL_OVERLOAD_MAX_WAIT_S` (default 300 s, about 5 min); when the next wait would exceed it, or when 6 re-tries are used, the cell becomes `failed` (code kept) and counts as a failed run for the breaker (R6d). The wait is a PROVIDER cooldown, not a per-cell sleep: the tick records `cooldown_until`, `overload_streak` on the `eval_slots/{provider}` doc (R6 per-provider cap), and while `now < cooldown_until` the scheduler claims no new slots for that provider in any eval run; sessions waiting on that provider stay `pending`, other providers keep filling. A successful run on the provider resets `overload_streak` and clears the cooldown. Cooldown state survives crashes (it lives on the slots doc) and needs no sleeping in the tick.
**R6c Failure isolation.** One run's failure never changes another run: a failed, waiting or skipped cell leaves every other cell, session, provider and eval run untouched, and the eval run continues to completion. The tick folds and fills each cell in its own try/except; an unexpected exception is logged (`tick_cell_error`, cell key, no payload), leaves the cell for the next tick, and after 3 consecutive handler errors on one cell marks only that cell `failed` (`scheduler_error`). A tick never aborts mid-way for one cell, and the next tick is enqueued first (R6 step 1), so a single bad cell cannot stop the chain.
**R6d Provider circuit breaker.** Per eval run and provider, `consecutive_failures[provider]` counts cells whose FINAL outcome is `failed` (after the internal retry and the overload budget are exhausted), in the order the tick folds them (by RunDoc `ended`). A `done` cell resets that provider's count to 0; `cancelled` cells do not count and do not reset; cells `skipped` or `waiting` do not count. When the count reaches `EVAL_PROVIDER_FAIL_LIMIT` (default 5, config), the provider is skipped for the rest of THAT eval run: every cell of that provider not yet started, including `waiting` cells, becomes `skipped` with reason `provider_unavailable` (counted in `skipped_units`), `provider_skips[provider]` records `{skipped_at, after_failures, skipped_cells}`, and no further cell of that provider is created. Runs already in progress on that provider finish and are kept (their outcome no longer changes the breaker); other providers continue unaffected; other eval runs are unaffected and the cooldown (R6b) is not forced. When all cells are terminal and any cell is `skipped`, the eval run status is `partial` (if at least one non-human run is `done`; otherwise `failed`). A cancelled eval run keeps `cancelled`-or-`partial` per R7 and still reports its `skipped` cells.
**R7 Cancel.** `POST /v1/runs/{id}/cancel` already exists (sets `cancel_requested`, finalizes queued units) [verified: `runs.py:493 cancel_run`; `repository.py:131,270`; run-detail button `Runs.tsx:180`] and is reworked for the group doc. Owner decision (2026-11-25): **no prod worker edit.** Semantics: Cancel stops NEW runs from starting; runs already in progress finish and are kept and shown (their outcome is `done` or `failed` as usual); cells not yet started, including `waiting` ones, become `cancelled` (reason `cancelled`); everything already completed is kept, readable and comparable. Cells already `skipped` stay `skipped`. Final status when all cells are terminal (i.e. the in-flight runs have finished): `partial` if at least one non-human run completed (`done`), else `cancelled` (matches today's rollup [verified: `runs.py:476-486`]). Idempotent: a second cancel changes nothing and returns the current status; cancelling a terminal run (`done|partial|failed|cancelled|deleting`) is a 200 no-op, an unknown id is 404. Allowed for any allowlisted user, same as delete (R8). Provider slots of in-flight runs (R6) free when each run is folded terminal; no slot is claimed after the request. In-flight runs finish and accrue their normal cost, recorded in `usage` on the RunDoc (so the "cancelled-run partial spend" question is moot: nothing is aborted, so nothing is partial); the owner accepted this because no further runs start.

## Architecture
```
eval web --(allowlist)--> eval-backend: POST /v1/runs
   ensure_session x N --> SessionDoc+TranscriptDoc (sid=fingerprint), gold/<sha>.json
   eval_runs/{id} (grouping) ; enqueue tick
tick (self re-enqueue ~10s) --> claim eval_slots/{provider} --> create_run(is_eval=True, run_id=det) --> start_run txn --> Cloud Task run
                                  one active run per session, <= 2 sessions in flight per provider (deployment-wide)
prod worker (same image/handler) --> RunDoc + ReportDoc + {uid}/{sid}/runs/{run_id}/*
eval-backend read --> group doc (progress) ; RunDocs/ReportDocs/gold (detail, compare)
```
Endpoint shapes:
| Endpoint | Shape change |
|---|---|
| `POST /v1/runs`, `/rerun` | none (body and reply same); rerun now reuses pinned sids |
| `POST /v1/runs/{id}/cancel` | same route; now idempotent (no-op when terminal), reply adds `cancelled_at`; stops new runs only (in-flight finish); final status `partial`/`cancelled` once in-flight runs end |
| `GET /v1/runs` | same fields from group doc; `status` may be `deleting`; adds `cancelled_at`, `skipped_units`, `provider_skips` |
| `GET /v1/runs/{id}` | `units[]`: `unit_id` = run id (human: `human-<sid>`), `session_id` still the dataset session id, new `run_id`, `prod_session_id`, `attempt`; `output` never inline (web already fetches when absent [verified: `Runs.tsx` `UnitOutput`]); `compare` same shape via legacy builder until SP06; unit `status` may be `waiting` (provider backing off) or `skipped` (reason `provider_unavailable`); adds `provider_skips[]` (`{provider, after_failures, skipped_cells, skipped_at}`) and `provider_cooldowns[]` (`{provider, cooldown_until}`) |
| `GET /v1/runs/{id}/units/{unit}/output` | same; source is ReportDoc (or gold) |
| `/v1/options`, `/v1/datasets*`, `/v1/uploads*`, `/v1/me`, `/healthz` | none (uploads move from `uploads/` to `eval-uploads/` prefix) |
| `POST /v1/runs/{id}/delete` | new |
| `/internal/tasks/unit` | removed; `tick`, `delete` added; `transcribe` kept |

Worked example: 12 sessions x 6 combos x 3 repeats = 216 RunDocs; with Anthropic and Gemini combos, at most 2 runs are active per provider (so <= 4 at once), each session runs its 18 runs in order, and a waiting session starts as a slot frees. The owner may close the browser; the run completes and History shows the result on return. Throughput is deliberately low; it is the owner's chosen spend/rate guard.

## Decisions
| # | Decision | Choice | Alternatives | Why |
|---|---|---|---|---|
| 1 | Session identity | `sid = fingerprint[:32]`, create-or-reuse | Firestore query by `(dataset_id, session_id)` | No index, race-free via exclusive create, pins transcript+goal+span so changed data never reuses a stale session |
| 2 | Owner uid | One shared eval uid | Uid per allowlisted email | Sessions are shared across users and runs; history is already global |
| 3 | Scheduler | Self-re-enqueued `tick` Cloud Task in eval-backend | Hook in prod worker; Cloud Scheduler sweep | No prod worker change; same pattern as eval's transcribe poll; no new infra |
| 4 | Refs location | Embedded in group doc | `units` subcollection | Item 4 removal; size bounded |
| 5 | Retry | `internal_error` -> 1 retry (new RunDoc attempt); provider overload (`upstream_unavailable`/`rate_limited`) -> cooldown + bounded re-tries (R6b); every other failure, incl. `code_version` drift, no retry | Eval-side in-unit loop; 2 retries 5 s/20 s for all transient; re-create on deploy drift | Owner round 2: retry only what may be our blip, treat capacity as backoff not failure; prod already retries transient once |
| 6 | Cancel | Stop new runs only; in-flight runs finish and are kept; keep completed; final `partial`/`cancelled`; idempotent; no prod worker edit | Prod session cancel; worker stage-boundary stop flag | Prod cancel is terminal on the shared session; owner: no prod worker edit, further runs are stopped anyway |
| 7 | Delete | Refuse while active, ordered idempotent steps, group doc last | Auto-cancel then delete; delete session too | Late worker writes would orphan blobs; sessions are shared |
| 8 | Gold | Copy to `gold/<sha256>.json` at import | Read datasets bucket at compare time | Decision 7; immune to dataset edits; one read path |
| 9 | Compare bridge | View adapter feeds legacy `build_compare` | Drop compare until SP06 | Existing screens keep working |
| 10 | Image | Separate eval-backend image that imports `onolys_api` | Add an eval `SERVICE_MODE` to the api image | Keeps public app free of eval routes; resolves SP03's open point |
| 11 | Concurrency | Config cap 2 per provider, deployment-wide, via transactional `eval_slots/{provider}` | Global in-flight cap of 20 | Owner: at most 2 interviews in parallel per AI provider; race-free across eval runs |
| 12 | Server-driven | All progress on tick + worker; GET only a safety net | Browser polling drives runs | Owner can leave the page |
| 13 | Overload | Scheduler layer above the engine's existing 429/529 backoff: provider cooldown + bounded re-tries (<= 300 s per cell) | Re-implement in-call backoff; treat as failure | Existing layer is bounded by the run deadline; capacity is a provider-wide state, not one run's fault |
| 14 | Isolation | Per-cell try/except; one cell never affects others | Fail the eval run on error | Owner: the eval run continues to completion |
| 15 | Provider breaker | 5 consecutive final failures per provider per eval run -> remaining cells `skipped` (`provider_unavailable`); config; status `partial` | No breaker; global stop | Avoids burning spend on a dead provider; other providers continue |
| 16 | Login | Reuse prod auth + eval allowlist; `eval/auth` removed (SP03) | Keep eval's own auth package | Owner: one login, one copy |

## Acceptance Criteria
- Import: same inputs -> same `sid`, one SessionDoc/TranscriptDoc, gold copied once; changed goal/span/transcript -> new `sid`; no `eval` field leaks into public session views or OpenAPI.
- Scheduler (fake queue/LLM): 3 sessions x 2 combos x 2 repeats never has two active RunDocs on a session; with combos on two providers and 2 eval runs at once, never more than 2 sessions with an active run per provider (cap from config, default 2; changing it changes behaviour); all 12 cells reach terminal; a crash between create and record yields no duplicate and no leaked slot; an `internal_error` run gets exactly one new attempt and then stays failed; other codes, incl. a `code_version`-failed run and `deadline_exceeded`, stay failed with no new run.
- Overload (fake clock, fake LLM that fails `upstream_unavailable`): the cell goes `waiting`, the provider cooldown stops new slot claims for that provider only while another provider keeps filling; waits grow 15 s doubling with jitter within `EVAL_OVERLOAD_MAX_WAIT_S` (default 300); a success resets the cooldown; a run still failing after the budget is `failed` and counts for the breaker; no code path re-implements or alters the engine's in-call 429/529 backoff (grep/diff gate: no edit under `engines/` or `jobs/`).
- Isolation: an exception while handling one cell is logged and leaves every other cell, session, provider and eval run progressing; the eval run still reaches a terminal status; 3 handler errors fail only that cell.
- Breaker: 5 consecutive final failures on one provider (config 5; test with 2) skip that provider's remaining cells (`skipped`, `provider_unavailable`, `skipped_units`, `provider_skips`) while the other provider completes; a success resets the count; cancelled cells do not count; in-flight runs finish and are kept; final status `partial` (or `failed` with no done run); another eval run is unaffected.
- Leave the page: with no GET issued after create, a fake-queue run reaches terminal; a later `GET /v1/runs` and `/v1/runs/{id}` show the live then final status and counters.
- Cancel (no worker edit): no new run starts after the request; unstarted and `waiting` cells become `cancelled`; runs in progress finish and are kept (`done` or `failed`); status stays `running` with `cancel_requested` until they end, then `partial` with `cancelled_at` when >=1 run completed, `cancelled` when none; completed runs/reports stay readable; a second cancel and a cancel on a terminal run are 200 no-ops; slots free as in-flight runs end; delete is still refused until terminal; diff gate: no change under `jobs/` or the worker.
- Delete: refused while active; after delete, that eval run's RunDocs, ReportDocs, report blobs and `runs/<id>/` files are gone and the group doc is gone; a second eval run on the same sessions keeps everything, and the sessions/transcripts/gold remain; killing the handler mid-way then retrying completes; History shows `deleting` then no row.
- Existing: name/description, saved_config rerun prefill, history search/filter/sort, config modal, unit progress, cost estimate, uploads, datasets catalog and once-per-session Human all pass their (rewritten) tests; `NewRun`/`Runs` vitest unchanged except Delete.
- Removed names (R9) have no remaining importers (grep gate); prod `api` tests untouched and passing.
- All tests offline: agents build and run offline tests only; no deploy, no terraform apply, no live LLM/STT eval run (the owner runs the first eval).
