## Must-fix
- [Bug Hunter] `eval/web/src/compare/LineView.tsx:14,37` with `CompareApp.tsx:70` and `compare_routes.py:_lanes` — the 3-lane cap only applies to rendering. The disagreement logic still uses the full, uncapped combo set:
  - **(a) Disagreement counts hidden combos.** `isDisagreement` falls back to the server's `data.disagreement`. The server computes it over every requested combo (`for key in v.keys`), and CompareApp sends the uncapped `state.combos`, or nothing, which means all run combos. Any run with more than 3 combos hits this by default (e.g. the 4-combo fixture with no `combos` param). The amber "Disagrees" row, the "N differing lines" chip and "Only disagreements" then include a combo whose lane is not on screen. A row can show three lanes that all match the human code and still be flagged.
  - **(b) The Combo filter can point at a hidden combo.** It is reachable from Deep dive: tick 4 combos, then open a confusion cell for D. `DeepDive.tsx:71` navigates with `combos:[A,B,C,D], combo:D, only:'disagree'`. The Line view then shows lanes A–C, but rows are filtered by D's disagreements and the prediction-code filter uses `[D]`. The Combo `<select>` has no D option, so it shows "All selected combos".
  - → Silent wrong output: the rows shown and flagged don't match the lanes shown.
  - **Fix:**
    1. Build `selected` so `state.combo`, when set, is always one of the shown lanes: put it first, then the others, then `.slice(0, MAX_LANES)`.
    2. Compute the no-`state.combo` branch on the client over the shown lanes: `(state.combo ? [state.combo] : selected).some(k => laneDisagrees(k, id))` in place of `data.disagreement[id]`. The alternative is to request lines with the capped combos.
    3. Add tests: 4 combos where only D disagrees on a turn, and `combos=[A,B,C,D], combo=D`.
