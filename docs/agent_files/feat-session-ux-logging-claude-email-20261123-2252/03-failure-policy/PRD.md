## TL;DR
Today every provider failure, including "model not found", maps to retryable `upstream_unavailable` [verified: `error_map._classify_llm` returns `(UPSTREAM, True)` for any `LLMError`; `docs/reference/staging-e2e.md:105-115`], and "Try again" exists only for the run step: a validate or transcribe failure forces a new upload [verified: `SessionPage.tsx:203`, `failureAction`]. This SP adds a three-way kind, a capped retry at every step, makes the limit rule "only a user/file fault is ever counted", and (owner rules) makes failures after a successful validation non-destructive (a retry and a future "retry with existing upload" reuse the blobs and docs), while a file that fails validation is an upload failure: purged, never a session (R11). It also stops charging interview sessions for an audio/relay mismatch (our error, R9) and serves the web pre-check limits from the API (R10).

## Problem
- No distinction between a blip and a broken config: the user is told to retry something that cannot succeed (anti-goal in the brief).
- Retry is unlimited and run-only (`start_run` on `failed`, no counter) [verified: `routes/runs.py:163`].
- Kind is implicit: `BAD_FILE_CODES` frozenset + `is_system_failure(code)` in `machine.py`; `error_map` returns `(code, retryable)` only; web re-derives from its own `UPLOAD_NEW` set. Three lists, one meaning.
- Second transient STT failure becomes `transcription_failed` ("Upload a different file") though the file is fine [verified: `error_map.to_public`, `stage="stt"` attempt>=2].
- Web has no copy for `output_invalid`, `deadline_exceeded`, `run_failed`; they fall to the generic message [verified: `errors.ts` MESSAGES].

## Goals / Non-Goals
**Goals:** one classifier; persisted kind; retry cap 3 per session enforced server-side; no unit lost to our faults; failures after validation never delete user data (R8); validation failure = upload failure (R11); interview audio mismatch is our error, never charged (R9); web pre-checks mirror server limits from one source (R10); copy and countdown per the locked table; reusable helpers for SP04/SP06.
**Non-goals:** logging fields (SP02); cancel state and charge-on-cancel (SP04); processing-screen layout (SP05); silent worker/LiteLLM retries (unchanged, `MAX_ATTEMPTS=2`); changing STT/LLM providers.

**R11 Validation failure = upload failure, not a session (owner 2026-11-23).** Applies to the file-check codes only: `audio_unreadable`, `audio_too_large`, `unsupported_audio`, `audio_too_long`, `interview_too_long` (the full set in `validate.py`; `rg 'fail\(ctx, "'` at coding confirms no others). Policy:
- On such a failure: `purge()` deletes the staged and stored audio (R8), and the session is removed: sessions are charged only at run start (`start_run`/`start_first_run`, R5, verified) so nothing was counted; it is not counted and not listed.
- Doc choice: delete the session doc (and its subcollections: recordings, runs) via a repo method `discard_failed_upload(uid, sid, code)`, and write a minimal `SessionStatusDoc` stub only (`uid`, `state="upload_failed"`, `error_code`, `updated_at`, `expire_at` = +7 days, no goal/audio/name/transcript data). Why a stub and not a hidden session doc: the open session page reads the status doc to learn what happened, so the reason must outlive the session doc; the stub holds no user data, is not in `listSessions` (the list reads session docs), and the logs, keyed by `session_id`, already carry everything for support. A full hidden session doc would keep user-entered data and need a state filter in every list/limit query. The stub is removed by a Firestore TTL policy on `expire_at` (add to the existing Firestore Terraform; if TTL policies are not available there, the existing stale sweep deletes stubs older than 7 days).
- `GET /sessions/{id}` on a discarded id returns 404 `not_found` (as any missing session).
- Web: while on the upload/session page, a status of `upload_failed` renders `UploadFailedView`: "Upload failed: <reason>. Choose a different file." with a button back to upload (`/sessions/new`), and the Reference line (session id). The reason text comes from the existing per-code copy (`errors.ts`, unchanged strings). If the user left and returns via a stale link: `GET /sessions/{id}` 404 → if the status stub exists show the same view, else a not-found notice ("This upload didn't go through, or the session no longer exists. Start a new upload."). Never shown in the sessions list.
- Retry-with-existing-upload (future) applies only to validated uploads.
- The other `validate` failures (transient infra errors, R9 mismatch) are ordinary session failures and keep their data.

## Architecture
```
exception -> error_map.classify() -> (code, kind)
   worker/_fail, stale, runs ──► SessionError{code,step,kind,counted} + status{error_kind,retries_left,counted}
run end: should_refund(kind, llm_started) -> release_once() -> counted
web: failureView(status) -> card | RetryButton(5s) -> POST /sessions/{id}/retry
retry: txn(retry_count+1, failed->step state) -> enqueue step | start_run
```
Interface: `classify(exc: BaseException, stage: Stage) -> Failure` ; `is_transient(exc: LLMError) -> bool` (engine-core, SP06 reuse).
