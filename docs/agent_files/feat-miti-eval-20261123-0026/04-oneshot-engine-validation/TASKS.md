## Task 1 — Core: dynamic schema, cost, `apply_coded_span`
What it is / what it means: Small additions to the core LLM client and helpers so a config-driven JSON schema can be sent and priced. (R3, R5, R10, Decisions 2, 3, 8)
What changes at a high level: `LLMRequest` gains `response_schema` (dict, mutually exclusive with `response_model`; parsed result is a plain dict). Add `to_provider_schema()` (strip unsupported keywords, inline refs, keep required/additionalProperties). `json_schema` mode sends it, `json_object` sends none. Fixture client keys on the schema text. Client computes per-call `cost_usd` via litellm, `None` if unpriced. Add pure `apply_coded_span` (half-open, SP1 R7). Truncation stays a non-retried bad-output error.
Done when: Tests first: both modes, mutual-exclusion error, schema conversion cases, stable fixture key, priced and unpriced cost, span slicing edges. Existing core tests unchanged and green.

## Task 2 — `run_validated` + `OutputInvalid`
What it is / what it means: The single validation-and-retry path for every engine, living in core so API and eval backend share it. (R8, Decisions 5, 6, owner D2)
What changes at a high level: Run engine, validate output against `engine.output_schema()`, return if clean. If invalid and `accepts_feedback`, set `ctx.feedback` from value-free issues plus the fixed instruction, re-run once. Otherwise, or if still invalid, raise `OutputInvalid` carrying attempts and first 10 issues. Usage from both attempts is summed.
Done when: Tests first with a stub engine: bad-then-good (feedback set, usage summed), bad-twice, good-first (one call), non-feedback engine fails at once with attempts 1, issues carry no values (PHI check). Lean `MitiEngine` golden report passes untouched.

## Task 3 — `onolys_oneshot` package skeleton, config loader, rendering
What it is / what it means: The generic engine package and how a config becomes a prompt. (R1, R2, R3)
What changes at a high level: New `engines/oneshot` workspace package depending only on core. Config loader reads `config.yaml`, `instructions.md`, `schema.json` from package data, validates `params` against `params_schema`, computes a config hash over all three. Renderer builds system (instructions, core footer, schema hint when enabled) and user (transcript lines with turn ids, whitelisted params JSON) after `coded_span` cut.
Done when: Tests first: AST test that nothing imports `onolys_miti`; unknown config raises `InputError`; bad params rejected; rendering order, ids, span restriction, hint on/off by mode; hash changes when any file changes.

## Task 4 — `OneshotEngine` run and usage
What it is / what it means: The engine itself: one call, temperature 0, no engine-side retry. (R4, R10)
What changes at a high level: `OneshotEngine` (`name=oneshot`, `accepts_feedback=True`) selects config via `params["config"]`, appends `ctx.feedback` after inputs when set, makes one `ctx.llm.complete` with `response_schema`, returns the dict plus `run_info` (config, hash, span, usage, model, route, structured output mode). `variants()` returns config names with the "One-shot · MITI" label. `output_schema()` returns the config schema.
Done when: Tests first with a fake LLM client: schema failure is not retried by the engine, feedback appears in the user message, run_info fields complete, usage carries tokens and cost, variants listed.

## Task 5 — MITI config, schema generator, golden fixtures
What it is / what it means: The first real config and its recorded tests. (R6, R7, R11, Decisions 1, 4, owner D1)
What changes at a high level: `configs/miti/` with instructions authored for one call from the lean prompts and pack items, `schema.json` limited to the 10 behavior counts, 4 globals and tips, generated by `scripts/gen_miti_schema.py` from the report schema. Record fixtures for `good_practice.json` and one short session (manual live recording step).
Done when: Tests first: every pack item id appears in the instructions (path-read, no MITI import); schema drift test passes; golden fixtures replay through `FixtureClient` and the output validates against the schema. Manual: send the subset schema in `json_schema` mode to the Gemini and Claude presets once, record the result.

## Task 6 — API rewiring and `output_invalid` error
What it is / what it means: The main app validates every engine through the wrapper, with a clear public error. (R8, R9, Decision 5)
What changes at a high level: `RealEvaluation` and the run job call `run_validated` instead of `run_miti` or `engine.run`. Remove `report_validator()`; the report schema comes from `MitiEngine.output_schema()`. Add public code `output_invalid` (not retryable, fixed message) in `error_map`, with `validation{attempts, first_issues}` on the run detail. The main api registry is not touched (M8).
Done when: Tests first: invalid lean output maps to `output_invalid` with no retry and no PHI in stored detail; engine `LLMBadOutput` mapping unchanged; valid golden run passes end to end; grep shows no engine is run outside the wrapper.

## Task 7 — One-shot scoring adapter
What it is / what it means: Makes one-shot results comparable with gold and lean. (R7, M2)
What changes at a high level: Add the oneshot adapter to `onolys_eval.adapters`, projecting the one-shot output to `Scores` the same way SP2's lean adapter does. R:Q and %CR come from counts by SP2's formula, so all engines are scored identically.
Done when: Tests first: adapter output matches a hand-built `Scores` from the recorded fixture; lean and oneshot adapters give equal `Scores` for equal counts; missing or extra fields surface as clear errors.

## Task 8 — Workspace and CI for oneshot

Add an `oneshot` CI job (and core/validated-run tests if SP3's job does not already cover them) plus change-detection flags, matching the existing `miti` job pattern. The api Dockerfile is untouched.
