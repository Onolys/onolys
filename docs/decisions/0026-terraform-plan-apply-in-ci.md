# 0026. Terraform plan on PRs, infra applied inside each deploy pipeline

**Audience:** contributors.

**Status:** accepted 2026-11-26 (revised the same day after review: apply moved from a separate after-merge workflow into the deploy pipelines). Amends [0022](0022-infra-gcp-terraform-two-environments.md) D1 ("run locally with ADC") and D5 (deploy auth only), and realizes the D18 `infra-plan.yml` item. Operating detail: [reference/infra-pipeline.md](../reference/infra-pipeline.md).

**Context.** Infrastructure was planned and applied by hand from one operator machine with git-ignored tfvars. That left drift between merged code and real infrastructure, no review of what a change does to the cloud, and a single machine as the only applier. A first design applied infrastructure from its own workflow after merge, independently of the app deploys. That lets the two land in either order: an app version can go live before the infrastructure it needs (a new secret, queue, IAM binding or env var), or an infrastructure apply can run under an app that does not expect it yet, and a prod rollback moved the app but not its infrastructure. The repository and its Actions logs are public, and pull requests from the same repository can run arbitrary workflow code.

**Decision.**

- **One pipeline per environment, infrastructure first.** `deploy-staging.yml`, `deploy-eval.yml` and `deploy-prod.yml` each plan their environment at the commit being deployed, apply that saved plan only if it has changes, then run the existing app jobs. A skipped apply (no changes) lets the app proceed; a failed plan or apply stops it. `terraform.yml` only plans PRs (one comment of resource addresses and actions, never values) and offers a manual read-only plan. Manual apply remains for bootstrap and break-glass only.
- **One approval for prod.** The infra apply uses the existing `production` environment (no separate infra environment) and becomes ready at the same moment as the app jobs, so one review click releases both; the app jobs then wait inside the job for the apply to succeed. The plan runs before the approval and its summary is in the run, so the reviewer approves what they read.
- **Rollback and promote apply infrastructure too.** A prod run for an older commit plans and applies that commit's infrastructure. A plan that would destroy the pipeline's own identities (a commit from before this pipeline) is blocked.
- **Keyless identities, two per project.** Plan: `terraform-plan`, metadata-only (a custom role of get/list permissions plus verified read-only predefined roles; data-read permissions and roles are denied, by a shared list enforced in the module's input validation and in tests), reachable by `terraform.yml` PR plans and by the project's deploy workflow through its own WIF pool. Apply: `terraform-apply`, project-admin-like, reachable only by the project's deploy workflow (`deploy-<env>.yml` on `main`, prod also on its `v*` release tags) with that workflow's trigger events, and for prod only from a job in `production`, through its own WIF pool. Shared steps are composite actions, not reusable workflows, so the OIDC `job_workflow_ref` claim stays the deploy workflow the provider matches. No service account keys.
- **Saved plans stay private.** The plan goes to the private state bucket (`plans/`, expired after 7 days); only hashes travel, as job outputs. The apply verifies the plan hash and the hash of the live deploy-managed inputs (`git_sha`, `llm_*`). With plan, apply and deploy in one run and one concurrency group per environment, pipeline runs no longer race; the input check stays as a cheap guard against out-of-band changes during a long approval wait.
- **Off until enabled.** Each environment's infra jobs are skipped, and its deploy behaves as before, until the owner bootstraps the identities and sets `TF_<ENV>_ENABLED=true`.
- **Not required checks.** The path-filtered PR plan jobs are not branch-protection checks (a skipped required check blocks unrelated PRs); the offline `infra` and `infra-isolated` jobs in `ci.yml` are.

**Consequences.** Merging an infra change changes nothing by itself; the next deploy of each environment applies it, right before the app that may depend on it (staging and eval after CI on `main`, prod on its approved release). A prod deploy can take longer (plan before approval, apply after it) and its app jobs hold runners while the apply runs. The apply identity is powerful, so its trust boundary is the deploy workflow file at the deployed ref and the `production` approval. Secrets and operator-only inputs stay out of Terraform. A new resource type must be added to the permission table or CI tests fail.
